SideProjectManager

사용 가이드

클라우드나 유료 서비스 없이 토이·사이드 프로젝트를 굴리기 위한 세 가지 도구의 사용법입니다. 공용 PC 한 대에서 돌아가는 통합 서버, 기획자와 개발자가 함께 쓰는 GitHub 이슈 기반 일정 관리, 그리고 새 프로젝트용 뼈대입니다. 역할별로 무엇을 하면 되는지는 프로젝트 관리 방법부터 보세요.

한눈에 보기

Local Hub공용 PC에 DB 같은 공통 서비스와 여러 프로젝트의 서비스를 함께 띄우고, git에 새 커밋이 올라오면 자동으로 다시 빌드합니다. 실패하면 이전 커밋으로 되돌리고 GitHub 이슈로 알립니다. 프로젝트 등록, 설정 버전 기록과 되돌리기, 버전 고정은 대시보드에서 합니다. 일정·할 일 자동 관리GitHub Issues와 Actions로 기획과 할 일을 연결해 진행률을 보고, 상태·마감 라벨, 매일 마감 알림, 주간 요약, Discord/Slack 알림을 돌립니다. 프로젝트 템플릿README, 기여 규칙, PR 양식, 기술 결정 기록, 언어를 알아서 감지하는 CI, Dependabot 설정을 한 번에 깔아 줍니다.
도구위치필요한 것비용
Local Hublocal-hub/Docker(Compose v2), Java 21, git무료 (내 PC)
일정·할 일 자동 관리.github/GitHub 저장소공개 저장소 무료, 비공개는 월 2,000분 무료 안에서 충분
프로젝트 템플릿template/없음무료
초기화 스크립트scripts/init-project.shbash (Windows는 Git Bash)무료

새 프로젝트에 적용하기

이 저장소를 받은 다음 초기화 스크립트로 원하는 도구를 프로젝트 폴더에 복사합니다. 옵션을 하나도 주지 않으면 세 가지를 모두 복사합니다.

git clone https://github.com/CASY82/SideProjectManager.git
SideProjectManager/scripts/init-project.sh ../my-project              # 템플릿 + 일정 자동화 + Local Hub
SideProjectManager/scripts/init-project.sh ../my-project --template   # 프로젝트 뼈대만
SideProjectManager/scripts/init-project.sh ../my-project --tasks      # 일정 자동화만
SideProjectManager/scripts/init-project.sh ../my-project --hub        # Local Hub 만

그다음 할 일은 스크립트가 마지막에 알려 줍니다. 자세한 옵션과 실제 출력은 init-project.sh 절에 있습니다.

프로젝트 관리 방법

기획, 일정, 할 일은 모두 GitHub 이슈로 등록하고, 진행 상태는 라벨과 하위 이슈로 저절로 관리됩니다. 사람이 하는 일은 양식에 맞춰 이슈를 쓰고, 담당자를 정하고, PR에 이슈 번호를 적는 것뿐입니다. 아래는 역할별로 무엇을 하면 되는지 순서대로 정리한 것입니다.

기획자          개발자                                자동으로
──────          ──────                                ──────
기획 이슈 작성 ─▶ 할 일로 나눠 등록 (관련 기획 #5) ──▶ 기획 아래 하위 이슈로 연결, status: todo
                 담당자에 나를 지정 ──────────────────▶ status: in-progress
                 PR 본문에 closes #12 ────────────────▶ status: review
                 PR 머지 ─────────────────────────────▶ 이슈 닫힘, 기획 진행률 올라감
결과 확인 후 ◀── 연결된 할 일이 모두 닫힘 ────────────── 기획자에게 확인 요청 댓글
기획 이슈 닫기
                 매일 09:00 마감 알림 · 월요일 09:00 주간 요약 (모두에게)

관리자: 처음 한 번 준비

  1. init-project.sh로 새 프로젝트를 만들고 GitHub에 푸시합니다(새 프로젝트에 적용하기).

  2. Actions → 라벨 동기화 → Run workflow를 한 번 눌러 상태·우선순위·마감·기획 라벨을 만듭니다.

  3. Settings → Collaborators → Add people로 팀원을 초대합니다. 개발자는 Write, 기획자는 Triage(이슈 작성·라벨·닫기만 가능)면 됩니다.

  4. Settings → Branches에서 main 보호(PR 필수, CI 통과 필수)를 켭니다.

  5. (선택) 채팅방 알림을 받으려면 Settings → Secrets에 DISCORD_WEBHOOK_URL 또는 SLACK_WEBHOOK_URL을 넣습니다(처음 설정).

  6. (선택) 보드로 보고 싶으면 칸반 보드를 만들고, 공용 PC가 있으면 Local Hub를 띄워 API 토큰을 정해 팀에 알리고, 대시보드에서 프로젝트를 등록하고 실패 이슈 알림을 켭니다.

기획자: 기획 등록과 확인

  1. New issue → 기획 양식으로 씁니다. 기획 의도, 목표와 성공 기준, 주요 내용은 꼭 적고, 이번에 하지 않는 것과 마감일도 적어 두면 일정이 덜 흔들립니다(양식 화면).

  2. 개발자의 질문과 답은 그 기획 이슈의 댓글로 주고받습니다. 결정 사항이 한곳에 남습니다.

  3. 진행 상황은 기획 이슈의 하위 이슈 목록과 진행률(예: 2/3), 그리고 월요일 주간 요약의 기획 진행률에서 봅니다.

  4. 연결된 할 일이 모두 끝나면 확인 요청 댓글이 옵니다. 결과가 의도대로면 기획 이슈를 닫고, 부족하면 댓글로 남겨 개발자가 할 일을 추가하게 합니다.

개발자: 할 일 등록부터 완료까지

  1. 기획을 읽고 일을 나눠 New issue → 할 일로 등록합니다. 관련 기획에 기획 번호(#5), 마감일, 우선순위를 적습니다. 기획과 상관없는 일이면 관련 기획은 비워 둡니다. 버그는 버그 양식을 씁니다.

  2. 내가 맡을 이슈의 Assignees에 나를 지정합니다. 상태가 status: in-progress로 바뀝니다.

  3. feat/12-login-api 같은 브랜치에서 작업하고, PR 본문에 closes #12를 적습니다. 이슈가 status: review가 됩니다.

  4. PR이 머지되면 이슈가 자동으로 닫히고 라벨이 정리되며, 연결된 기획의 진행률이 올라갑니다.

  5. 일정이 바뀌면 이슈 본문의 마감일만 고칩니다. due-soon, overdue 라벨과 알림이 알아서 다시 계산됩니다.

  6. 공용 PC에서 내 커밋 배포가 실패하면 나를 멘션한 실패 이슈가 올라옵니다. 고쳐서 푸시하면 배포가 성공하는 순간 이슈가 닫힙니다. 언제부터 깨졌는지는 대시보드 배포 이력에서, 시연 전에 버전을 묶어 두려면 버전 고정을 씁니다.

보고 싶은 것어디서

Local Hub

공용 PC 통합 서버

팀 공용 PC나 집 서버 한 대에서 공통 서비스(Postgres, Redis 등)와 여러 프로젝트의 서비스를 함께 띄워 둡니다. 각 서비스 저장소를 주기적으로 확인하다가 새 커밋이 보이면 그 서비스만 다시 빌드하고 재기동합니다. 프로젝트 추가, 설정 편집, 버전 기록과 되돌리기, 버전 고정까지 모두 웹 대시보드(기본 8090 포트)에서 합니다.

 팀원 A ─push─▶ GitHub (shop/api)  ┐
 팀원 B ─push─▶ GitHub (blog/web)  ┤   git fetch (폴링)
                                   ▼
 ┌──────────── 공용 PC ──────────────────────────────────────────┐
 │  Local Hub (Spring Boot, :8090 대시보드)                       │
 │    프로젝트 추가·설정 편집·버전 기록 / 새 커밋 → 다시 빌드·기동  │
 │    실패하면 이전 커밋으로 되돌려 다시 기동                       │
 │                                                               │
 │  docker 네트워크 "sidehub"                                     │
 │    sidehub        postgres redis mysql rabbitmq   (공통)       │
 │    sidehub-shop   api  admin                      (프로젝트 1) │
 │    sidehub-blog   web                             (프로젝트 2) │
 └───────────────────────────────────────────────────────────────┘

설치와 실행

준비물

  • Docker (Docker Desktop, 또는 Docker Engine과 Compose v2)
  • Java 21 이상. Maven은 따로 깔지 않아도 mvnw가 받아 옵니다.
  • git, 그리고 감시할 저장소를 읽을 수 있는 권한 (비공개 저장소 참고)
  • 감시할 각 서비스 저장소의 루트에 Dockerfile

  1. local-hub 폴더에서 실행 스크립트를 돌립니다. 처음 실행하면 hub.example.yml을 hub.yml로 복사하고 앱을 빌드합니다.

    cd local-hub
./hub.sh             # Windows 는 hub.cmd
./hub.sh --rebuild   # 이 저장소를 pull 받은 뒤 앱을 다시 빌드할 때

  2. hub.yml에는 PC 전체에 적용되는 공통 설정만 있습니다. 보통은 함께 띄울 공통 서비스(infra-profiles)만 확인하면 됩니다. 감시할 저장소는 여기가 아니라 대시보드에서 프로젝트별로 등록합니다. 팀원들이 각자 PC에서 배포 버튼을 누르거나 설정을 고치게 하려면 api-token도 꼭 넣으세요(API와 토큰). 이 파일은 팀마다 다르므로 git에 올리지 않습니다.

    hub:
  data-dir: data                    # 프로젝트 설정·버전 기록·작업 공간·배포 이력. 백업은 이 폴더 복사
  project-name: sidehub             # 공통 서비스의 compose 프로젝트 이름. 각 프로젝트는 sidehub-<id>
  network: sidehub                  # 공통 서비스와 모든 프로젝트가 함께 쓰는 docker 네트워크
  infra-profiles: [postgres, redis] # 시작할 때 같이 띄울 공통 서비스
  poll-interval: 60s                # 새 커밋 확인 주기 (30s, 1m, 5m ...)
  command-timeout: 15m              # git/docker 명령 하나가 이보다 오래 걸리면 실패
  api-token: ""                     # 비우면 Hub PC 자신에서만 변경 가능. 팀이 함께 쓰려면 긴 임의 문자열을 넣을 것
  allowed-hosts: []                 # hub-pc.local 처럼 호스트 이름으로 접속할 때만 적음
  issues:
    enabled: false                  # 실패를 GitHub 이슈로 알리기 (아래 참고)

  3. 브라우저에서 http://<공용PC IP>:8090을 열고, 아래 순서로 첫 프로젝트를 등록합니다.

프로젝트 등록하기

프로젝트 하나는 함께 배포되는 서비스 묶음입니다. 예를 들어 "쇼핑몰" 프로젝트에 주문 API와 관리자 화면 저장소를 넣고, "블로그" 프로젝트는 따로 만듭니다.

  1. 왼쪽 아래 새 프로젝트에 id(영문 소문자·숫자·-, 예: shop)와 이름을 적고 추가를 누릅니다.

  2. 설정 탭 project.yml에 감시할 저장소를 적고, 변경 메시지를 쓴 뒤 저장합니다. 아직 compose.yml에 서비스 정의가 없으므로 서비스 탭에는 대기로 보입니다.

    # project.yml
name: 쇼핑몰
description: 주문·결제 서비스
services:
  - name: api
    repo: https://github.com/my-team/shop-api.git
    branch: main
  - name: admin
    repo: git@github.com:my-team/shop-admin.git
    branch: main
    # compose-service: admin-web   # compose 서비스 이름이 name 과 다를 때만
    # issue-repo: my-team/shop     # 실패 이슈를 다른 저장소에 모을 때만

  3. compose.yml로 바꿔 같은 이름의 서비스를 정의하고 저장합니다. 저장하면 바로 저장소를 받아 빌드·기동합니다. 저장소는 workspace/<서비스 이름>에 받아지므로 build를 그 경로로 둡니다. 맨 아래 networks 부분은 그대로 두세요. 공통 서비스와 같은 네트워크에 붙어서 DB 주소를 localhost가 아니라 postgres:5432로 씁니다.

    # compose.yml
services:
  api:
    build: ./workspace/api
    restart: unless-stopped
    ports: ["8080:8080"]
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/app
      SPRING_DATA_REDIS_HOST: redis
  admin:
    build: ./workspace/admin
    ports: ["8081:80"]

networks:
  default:
    name: sidehub
    external: true

  4. 서비스 탭에서 상태가 실행 중이 되는지 확인합니다.

저장 순서는 상관없습니다 compose.yml에 정의가 없는 서비스는 배포하지 않고 대기 상태로 "compose.yml 에 'api' 서비스 정의가 필요해요"를 보여 줍니다. 실패 이력이나 실패 이슈는 남지 않고, 정의를 저장하는 순간 바로 배포됩니다.

대시보드

왼쪽에 프로젝트 목록과 공통 서비스 상태가 있고, 프로젝트를 고르면 서비스, 설정, 배포 이력, 설정 버전 네 탭이 나옵니다. 실패하거나 되돌린 서비스가 있는 프로젝트에는 목록에 문제 표시가 붙습니다. 화면은 저절로 새로고침됩니다.

버튼하는 일
지금 확인폴링 주기를 기다리지 않고 바로 새 커밋을 확인합니다. 바뀐 게 있으면 배포합니다.
다시 배포커밋이 그대로여도 다시 빌드·기동합니다. 실패한 커밋을 다시 시도할 때도 씁니다.
버전 고정브랜치 최신 대신 특정 커밋이나 태그로 고정합니다(버전 고정).
컨테이너 로그해당 서비스 컨테이너의 최근 로그 200줄을 펼칩니다.
배포 출력마지막 배포 때 docker compose가 남긴 빌드·기동 출력을 펼칩니다. 실패 원인을 볼 때 씁니다.

상태뜻
대기아직 한 번도 확인하지 않았거나, compose.yml에 그 서비스 정의가 아직 없음
실행 중최신 커밋(또는 고정한 버전)으로 떠 있음
배포 중새 커밋을 빌드·기동하는 중. 끝날 때까지 기존 컨테이너는 그대로 떠 있음
되돌림새 커밋 배포에 실패해서 이전 커밋으로 되돌림. 서비스는 이전 버전으로 계속 떠 있음
실패배포에 실패했는데 되돌릴 이전 커밋이 없음(첫 배포), 되돌린 버전도 실패, 또는 git 명령 자체가 실패

공통 서비스와 다른 화면

배포 규칙

상황Local Hub가 하는 일
처음 시작sidehub 네트워크를 만들고 infra-profiles의 공통 서비스를 올린 뒤, 모든 프로젝트의 서비스를 확인
새 커밋 발견그 서비스만 docker compose up -d --build --no-deps --wait로 다시 기동

실패한 커밋이 그대로매 주기마다 다시 시도하지 않음. 새 커밋이 오거나 "다시 배포"를 누르면 재시도
project.yml 저장새로 추가된 서비스를 바로 받아서 기동 (compose.yml에 정의가 없으면 대기)
compose.yml 저장, 설정 되돌리기그 프로젝트의 모든 서비스를 다시 기동해 바뀐 설정을 반영
버전 고정 중브랜치에 새 커밋이 와도 고정한 버전을 유지
커밋 변화 없음아무것도 하지 않음
  • --wait를 쓰므로 Compose에 healthcheck를 적어 두면 헬스체크까지 통과해야 성공으로 봅니다. 없으면 컨테이너가 떠 있기만 하면 성공입니다.
  • --no-deps라서 한 서비스를 다시 띄워도 DB 같은 다른 컨테이너는 건드리지 않습니다.
  • workspace/는 배포 전용입니다. 배포할 때 git reset --hard를 하므로 그 안에서 코드를 직접 고치지 마세요.
  • 같은 서비스의 배포는 한 번에 하나만 돕니다. 배포 중에 버튼을 다시 눌러도 겹쳐 돌지 않습니다.

배포 이력

서비스가 배포에 성공하거나 실패하거나 되돌려질 때마다 배포 이력 탭에 시각, 서비스, 결과, 커밋, 메시지가 쌓입니다. "어제 저녁엔 잘 됐는데 언제부터 깨졌지?"를 확인할 때 씁니다.

설정 버전: 비교와 되돌리기

project.yml, compose.yml, 버전 고정이 바뀔 때마다 프로젝트 폴더의 git 저장소에 한 버전씩 커밋됩니다. 저장할 때 적은 메시지가 그 버전의 설명이 됩니다.

  • 이 버전으로 되돌리기를 누르면 그때의 설정 파일로 돌아가고 프로젝트의 서비스를 모두 다시 배포합니다.
  • 되돌린 것도 새 버전으로 남기 때문에 이력은 지워지지 않습니다. 되돌리기를 잘못 눌렀다면 바로 앞 버전으로 다시 되돌리면 됩니다.
  • 서비스 코드의 버전이 아니라 Local Hub 설정의 버전입니다. 코드를 예전 커밋으로 돌리고 싶으면 버전 고정을 씁니다.

버전 고정

서비스 카드의 버전 고정에서 브랜치 최신 대신 특정 커밋이나 태그로 고정할 수 있습니다. 시연이나 QA 기간처럼 화면이 바뀌면 안 될 때, 또는 최신 커밋에 문제가 있어 잠시 예전 버전으로 돌리고 싶을 때 씁니다.

  • 고정한 서비스에는 카드에 📌 v1.0 고정처럼 표시됩니다.
  • 고정 풀기를 누르면 다시 브랜치 최신을 따라갑니다.
  • 고정과 해제도 설정 버전으로 기록되므로 언제 무엇으로 고정했는지 남습니다.

여러 프로젝트 함께 돌리기

프로젝트마다 설정과 compose 파일이 따로 있고, sidehub-<id>라는 별도의 compose 프로젝트로 뜹니다. 모든 프로젝트가 같은 docker 네트워크(sidehub)에 붙기 때문에 공통 서비스는 postgres:5432처럼 이름으로 함께 씁니다.

  • 한 PC에서 함께 돌기 때문에 ports는 프로젝트끼리 겹치지 않게 정하세요. 예를 들어 쇼핑몰은 8080·8081, 블로그는 3000.
  • 같은 DB 서버를 쓰더라도 프로젝트마다 DB 이름이나 스키마를 나누는 것을 추천합니다.
  • 프로젝트를 삭제하면(설정 탭 아래) 그 프로젝트의 컨테이너를 내리고 설정, 버전 기록, 작업 공간을 지웁니다. 공통 서비스와 볼륨은 남습니다.

모든 데이터는 DB 없이 local-hub/data/ 아래 파일로 저장됩니다. 백업은 이 폴더를 복사하면 됩니다.

data/projects/shop/
  project.yml    이름, 설명, 서비스 저장소 목록
  compose.yml    이 프로젝트의 docker compose 정의
  pins.yml       버전 고정 목록 (있을 때만)
  .git/          설정 버전 기록
  workspace/     서비스 저장소 clone (배포 전용)
  history/       배포 이력 (deploys.tsv)

실패를 GitHub 이슈로 알리기

켜 두면 배포가 실패하거나 되돌려질 때 그 서비스 저장소에 이슈가 자동으로 올라가고, 커밋 작성자가 멘션됩니다. 다음 배포가 성공하면 댓글을 남기고 이슈를 닫습니다. 대시보드를 보고 있지 않아도 실패를 놓치지 않게 하는 기능입니다.

# hub.yml
hub:
  issues:
    enabled: true
    token: ${HUB_GITHUB_TOKEN:}       # 토큰은 파일에 적지 말고 환경 변수로
    labels: [local-hub, "type: bug"]  # 첫 번째 라벨로 기존 이슈를 찾음
    include-output: true              # 빌드 출력 끝부분(80줄)을 이슈에 넣을지
export HUB_GITHUB_TOKEN=github_pat_...   # Windows: set HUB_GITHUB_TOKEN=...
./hub.sh

이슈를 올릴 저장소는 서비스의 repo 주소(github.com/owner/repo)에서 알아냅니다. 여러 서비스의 이슈를 한 저장소에 모으고 싶거나 GitHub가 아닌 주소라면, 대시보드 project.yml의 서비스마다 issue-repo: owner/repo를 적습니다.

상황이슈에 생기는 일
배포 실패·되돌림[Local Hub] <프로젝트>/<서비스> 배포 실패 이슈 생성. 실패한 커밋, 상태, 빌드 출력 끝부분, 커밋 작성자 멘션
이슈가 열린 채로 다른 커밋도 실패같은 이슈에 댓글 추가 (서비스마다 이슈는 하나)
같은 실패가 계속됨아무것도 하지 않음. 매 주기마다 댓글이 쌓이지 않음
다음 배포 성공"정상으로 돌아왔어요" 댓글을 남기고 닫음. Local Hub를 재시작한 뒤의 첫 성공도 포함
  • 토큰: GitHub Settings → Developer settings → Fine-grained tokens에서 대상 저장소를 고르고 Issues: Read and write, Contents: Read-only로 만듭니다. Contents 권한은 커밋 작성자의 GitHub 계정을 찾는 데만 씁니다.
  • 이슈에 type: bug 라벨이 붙으므로 아래 일정 자동화의 마감 알림과 주간 요약에도 그대로 잡힙니다.
  • 공개 저장소라면 빌드 출력에 비밀 값이 찍히지 않는지 확인하고, 걱정되면 include-output: false로 둡니다.
  • GitHub에 연결할 수 없어도 배포는 그대로 진행되고, 다음 실패 때 다시 시도합니다.

조회(GET)는 토큰 없이 됩니다. 배포, 설정 저장, 버전 고정, 되돌리기, 프로젝트 추가·삭제 같은 변경 요청은 아래 규칙을 따릅니다.

hub.api-token변경 요청
비어 있음 (기본)Hub PC 자신(localhost)에서만 됩니다. 다른 PC에서 보내면 403
설정함어느 PC에서든 X-Hub-Token 헤더에 같은 값을 보내야 됩니다. 틀리면 401
공용 PC로 여럿이 쓰려면 토큰을 꼭 설정하세요 hub.api-token에 긴 임의 문자열을 넣고 팀원에게 알려 줍니다. 대시보드에서는 왼쪽 아래 API 토큰 칸에 한 번 넣으면 그 브라우저에 기억됩니다. 토큰이 없으면 다른 PC에서는 화면은 보이지만 버튼을 누르면 403이 납니다.
  • 다른 사이트가 브라우저를 통해 몰래 보내는 요청(Origin이 다른 변경 요청)은 막습니다.
  • 모르는 호스트 이름으로 들어온 요청은 조회도 403으로 막습니다. localhost와 IP 주소(http://192.168.0.10:8090)는 그대로 되고, http://hub-pc.local:8090처럼 이름으로 접속한다면 hub.yml에 적어 둡니다.
hub:
  api-token: "길고-임의로-만든-문자열"
  allowed-hosts: [hub-pc.local]

공용 PC는 보통 밖에서 접속할 수 없어 GitHub 웹훅을 직접 받기 어렵습니다. 그래서 기본은 폴링입니다. 더 빨리 반영하고 싶으면 poll-interval을 15s 정도로 줄이거나, 같은 네트워크에서 아래처럼 호출하면 됩니다.

curl -X POST -H "X-Hub-Token: <토큰>" http://<공용PC>:8090/api/projects/shop/services/api/deploy

docker network create sidehub
docker compose --profile postgres --profile redis up -d

비공개 저장소

Local Hub는 호스트의 git을 그대로 씁니다. 공용 PC에서 git clone이 되면 Local Hub도 됩니다.

  • SSH: 공용 PC에 배포용 SSH 키를 만들고 각 저장소 Settings → Deploy keys에 읽기 전용으로 등록한 뒤 repo: git@github.com:team/api.git
  • HTTPS: git config --global credential.helper store 후 한 번 clone해서 토큰을 저장

비밀번호를 묻는 상황이 되면 멈춰서 기다리지 않고 실패로 표시합니다.

메모리는 hub.sh 기준 힙 256MB, SerialGC로 돌며 서비스 몇 개를 감시할 때 약 170MB를 씁니다. 무거운 건 Docker 빌드이므로 공용 PC 사양은 팀원 서비스 크기에 맞추면 됩니다.

처음 설정 (5분)

  1. .github/를 프로젝트에 복사합니다: scripts/init-project.sh ../my-project --tasks

  2. GitHub에 푸시한 뒤 Actions 탭 → 라벨 동기화 → Run workflow를 한 번 누릅니다. 라벨 13개가 만들어집니다.

  3. (선택) 채팅방 알림을 받으려면 Settings → Secrets and variables → Actions → New repository secret에 추가합니다.

    • Discord: 채널 설정 → 연동 → 웹후크에서 만든 URL을 DISCORD_WEBHOOK_URL로
    • Slack: Incoming Webhook URL을 SLACK_WEBHOOK_URL로

    둘 다 넣으면 두 곳 모두로 보냅니다. 없으면 알림 없이 라벨과 이슈만 정리합니다.

  4. 바로 확인하고 싶으면 Actions → 마감 알림 → Run workflow를 누릅니다.

기획자와 함께 쓰기

기획자는 코드를 몰라도 GitHub 이슈만으로 참여할 수 있습니다. 기획자가 왜 무엇을 만드는지 기획 이슈로 쓰고, 개발자가 그걸 할 일로 나눠 연결하면, 기획 이슈에서 진행률을 보고 끝나면 확인 요청을 받습니다.

기획자: 기획 이슈 작성 (#5)          개발자: 할 일 이슈 작성, "관련 기획" 에 #5
   기획 의도 · 목표와 성공 기준   ──▶     #12 온보딩 안내 화면  ┐
   주요 내용 · 하지 않는 것                #13 건너뛰기 처리     ├─ #5 아래 하위 이슈로 자동 연결
   참고 자료 · 마감일                      #14 첫 글쓰기 이동    ┘
        ▲                                      │ 모두 닫히면
        └──── "@기획자 확인해 주세요" 댓글 ◀────┘

  1. 기획자가 New issue → 기획 양식으로 씁니다. 기획 의도, 목표와 성공 기준, 주요 내용은 필수이고, 이번에 하지 않는 것과 참고 자료(Figma 링크, 이미지를 끌어다 놓기)를 적으면 개발 일정이 덜 흔들립니다.

  2. 개발자가 기획을 읽고 일을 나눠 할 일을 만들며, 관련 기획 칸에 기획 번호를 적습니다. 그러면 할 일이 기획의 하위 이슈로 붙고, 기획 이슈에 진행률 막대가 생깁니다. 질문은 기획 이슈 댓글로 주고받으면 기록이 한곳에 모입니다.

  3. 연결된 할 일이 모두 닫히면 자동화가 기획 작성자를 멘션해 확인을 요청합니다. 의도대로 됐으면 기획자가 기획 이슈를 닫습니다. "계획 없음"으로 닫은 할 일은 완료로 치지 않습니다.

  4. 매주 월요일 주간 요약의 기획 진행률에 기획마다 완료/전체가 나옵니다(알림 예시 참고).

기획자 권한은 Triage면 충분합니다 저장소 Settings → Collaborators → Add people에서 역할을 Triage로 고르세요. 이슈 작성, 라벨, 닫기는 되고 코드는 고칠 수 없습니다. 비공개 저장소에서도 무료입니다.

하위 이슈 기능을 쓸 수 없는 환경이면 기획 이슈에 "할 일 #12 가 이 기획에 연결됐어요" 댓글로 대신 남깁니다. 관련 기획 번호가 없는 이슈를 가리키면 할 일 이슈에 안내 댓글이 달립니다.

라벨

.github/labels.json에 정의된 라벨입니다. 상태·우선순위·마감 라벨은 그룹마다 하나만 남도록 자동으로 맞춥니다.

type: task type: bug type: planning status: todo status: in-progress status: review priority: P0 priority: P1 priority: P2 due-soon overdue weekly-summary local-hub
  • due-soon: 마감 2일 이내 (오늘 포함)
  • overdue: 마감일이 지남. 처음 붙을 때 담당자를 멘션하는 댓글이 한 번 달림
  • status: review: 같은 저장소 브랜치에서 올린 PR이 이슈를 closes로 연결했을 때
  • type: planning: 기획 양식으로 쓴 이슈. 주간 요약의 담당자별 목록에서는 빠지고 기획 진행률에 나옴
  • local-hub: Local Hub가 자동으로 올린 배포 실패 이슈

알림 예시

아래 두 화면의 본문은 저장소의 알림 스크립트(.github/scripts/lib.js)에 예시 이슈를 넣어 실제로 만든 것입니다. 2026-11-02(월) 기준이고, 이슈와 사람은 예시입니다. 화면 모양은 미리보기이고 실제 GitHub나 채팅 앱 화면은 아닙니다.

주간 요약은 주간 요약 2026-11-02 같은 제목의 이슈로 만들어지고 weekly-summary 라벨이 붙습니다. "계획 없음(Close as not planned)"으로 닫은 이슈는 완료 목록에서 빠집니다.

칸반 보드로 보기

라벨만으로도 충분하지만 보드로 보고 싶다면 GitHub Projects(무료)를 씁니다.

  1. 저장소의 Projects → New project → Board로 프로젝트를 만듭니다.

  2. 오른쪽 위 … → Workflows에서 Auto-add to project를 필터 is:issue로 켭니다. Item closed, Pull request merged는 기본으로 켜져 있어 Done으로 옮겨 줍니다.

  3. 라벨로 묶어 보고 싶으면 보기 설정에서 Group by → Labels를 고릅니다.

무료 플랜의 Auto-add 개수 제한에 걸리면 저장소 변수 PROJECT_URL(프로젝트 주소)과 시크릿 PROJECT_TOKEN(project 권한이 있는 개인 토큰)을 넣으세요. 그러면 issue-automation.yml이 대신 보드에 추가합니다.

비용과 주의점

  • 공개 저장소는 Actions가 무료이고 제한이 없습니다. 비공개 저장소는 월 2,000분 무료인데, 이벤트 처리 한 번이 10~20초라 매일 알림과 주간 요약을 합쳐도 한 달 수십 분 수준입니다.
  • 예약 실행(cron)은 GitHub 사정으로 몇 분에서 수십 분 늦게 돌 수 있습니다.
  • 공개 저장소에 60일 동안 커밋이 없으면 GitHub가 예약 워크플로를 멈춥니다. Actions 탭에서 다시 켜면 됩니다.
  • 포크에서 온 PR은 권한이 읽기 전용이라 status: review가 붙지 않습니다.
  • 이슈 제목에 <!channel>, @everyone 같은 문구가 있어도 채팅 알림이 채널 전체에 멘션되지 않습니다. Slack은 제어 문자를 글자 그대로 바꿔 보내고, Discord는 멘션을 꺼 두고 보냅니다.
  • 마감 알림이나 주간 요약을 손으로 실행할 때 기준 날짜를 넣는다면 YYYY-MM-DD 형식이어야 합니다. 형식이 틀리면 라벨을 건드리지 않고 실행을 멈춥니다.
