# 함께 일하는 규칙

처음 합류했다면 이 문서만 읽으면 됩니다. 규칙을 바꾸고 싶으면 이 파일을 고치는 PR 을 올려 주세요.

## 1. 일 시작하기

0. 새 기능은 기획자가 먼저 **기획** 이슈로 씁니다 (기획 의도, 목표와 성공 기준, 주요 내용).
   개발자는 기획을 읽고 일을 나눠 할 일을 만들며, 할 일의 **관련 기획** 칸에 기획 번호를 적습니다.
1. 할 일은 먼저 **이슈** 로 만듭니다 (New issue → 할 일). 마감일과 우선순위를 적어 주세요.
2. 내가 맡을 이슈에 자신을 **Assignees** 로 지정합니다. 상태 라벨이 자동으로 `진행 중` 으로 바뀝니다.

## 2. 브랜치

`main` 은 항상 실행 가능한 상태로 둡니다. 직접 푸시하지 않고 PR 로만 합칩니다.

| 종류 | 이름 | 예시 |
| --- | --- | --- |
| 기능 | `feat/<이슈번호>-<짧은설명>` | `feat/12-login-api` |
| 버그 | `fix/<이슈번호>-<짧은설명>` | `fix/31-null-token` |
| 그 외 | `chore/...`, `docs/...` | `docs/readme-setup` |

## 3. 커밋 메시지

[Conventional Commits](https://www.conventionalcommits.org/ko/) 형식을 씁니다.

```
feat: 로그인 API 추가
fix: 토큰이 없을 때 500 에러 수정
docs: 실행 방법 보완
refactor: 사용자 서비스 분리
test: 주문 취소 테스트 추가
chore: 의존성 업데이트
```

## 4. PR

- 본문에 `closes #12` 를 쓰면 이슈가 `리뷰 중` 이 되고, 머지되면 자동으로 닫힙니다.
- 리뷰어 1명 이상 승인 후 머지합니다. 머지 방식은 **Squash and merge** 를 기본으로 합니다.
- CI 가 빨간불이면 머지하지 않습니다.
- PR 은 작게. 한 PR 에 한 가지 일만 담는 게 리뷰가 빠릅니다.

## 5. 리뷰

- 24시간 안에 첫 리뷰를 다는 것을 목표로 합니다.
- 반드시 고쳐야 하는 것과 제안을 구분해 주세요. 제안은 앞에 `nit:` 을 붙입니다.

## 6. 기술 결정 기록

라이브러리 선택, 구조 변경처럼 나중에 "왜 이렇게 했지?" 싶을 결정은
[docs/decisions](docs/decisions/) 에 짧게 남깁니다.
